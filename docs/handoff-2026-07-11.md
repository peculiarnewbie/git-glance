# Handoff — repository awareness, local API, and HTTP/SSE migration

## Product direction

Git Glance should remain a useful repository dashboard, but its larger role is
to be a **local repository-awareness service**. AI clients should query its
structured, current repository facts and do their own reasoning/conversation.
Git Glance should not become an AI workbench or a built-in chatbot.

The intended future MCP surface is therefore facts-first: repository discovery,
workspace status, repository status, search, activity, and bounded diffs. An
MCP adapter should initially be read-only and local/stdio.

## Decisions made

- Removed the former peer-device/multi-machine feature completely. It was not
  retained as dormant code because any future cross-machine design should be
  reconsidered from first principles.
- Kept Git Glance single-machine and local-repository focused.
- Replaced the browser-facing WebSocket protocol with conventional JSON HTTP
  endpoints plus one server-sent-event stream.
- Kept the existing Git/action implementation as an internal transition layer;
  its `ws.rs` filename and `WSRequest`/`WSResponse` names are legacy internal
  names only. They do not expose or create WebSocket connections.

## Current API contract

The complete endpoint reference is in [core-api.md](core-api.md).

- Read and direct action calls use JSON under `/api`.
- `POST /api/operations/{scan,scan-only,commit,fetch}` returns an
  `operationId`.
- `GET /api/events` is the single SSE stream. It emits `progress`, `done`, and
  `error` events containing the matching `operationId`.
- The frontend opens SSE before creating an operation, so it does not lose the
  initial progress event.

The packaged Electrobun view uses the local server at `127.0.0.1:3451`. CORS
is intentionally restricted to the `views://mainview` origin. Vite development
proxies `/api` to the local server.

## Important remaining work

### Security and remote UI split

The service still binds to `0.0.0.0:3451`. HTTP/SSE is a transport improvement,
not a remote-access security boundary. Do not consider the raw API safe to
expose to a broader network yet.

The recommended next architecture is:

```text
Remote browser
  -> authenticated UI gateway (HTTPS/SSE, limited UI actions)
  -> private Git core (loopback/in-process)
  -> local stdio MCP adapter
```

The public gateway should default to read-only and should not simply proxy the
entire raw Git API. Network authentication belongs at the gateway or reverse
proxy; local stdio MCP does not need network authentication.

### MCP

MCP is still not implemented. The smallest useful next step is a local stdio
adapter exposing only the read API: list repositories, workspace status,
repository status, repository search, recent activity, and bounded diff.
Leave pull, push, scan, and commit out of MCP initially.

### Internal cleanup

`packages/server-rust/src/ws.rs` now acts as the internal action dispatcher.
It should eventually be renamed/refactored into a transport-neutral core module
with transport-neutral request/response types. This is a cleanup, not a
remaining WebSocket capability.

### Deferred feature

Historical snapshots of uncommitted working-tree changes were deliberately not
implemented. They require explicit decisions about storage, retention, and
what should count as a meaningful change between scans.
